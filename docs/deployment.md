# Free-tier deployment

This procedure uses a dedicated Supabase Free project, a Render Free web service, and a Render
static site. It requires owner access to both accounts. Do not choose a paid database, worker,
instance, custom SMTP domain, or automatic billing upgrade.

## 1. Prepare Supabase

Create a dedicated project. Set `SUPABASE_ANON_KEY` to its publishable key and
`SUPABASE_SERVICE_ROLE_KEY` to a backend secret key from the project's API Keys page.
The existing variable names also accept legacy anon and service-role JWTs.
Store the backend secret in the server environment.
Use an asymmetric Supabase JWT signing key (ES256 or RS256), because FastAPI verifies staff tokens
against the project's JWKS endpoint.

Disable public user signup. Create and confirm the initial admin's email/password account in the
Supabase Auth dashboard. Record its UUID. The application has no self-service staff signup.

Copy the **Session pooler** connection string from Connect, normally port 5432. Use the password
for the correct project and URL-encode special characters. Require TLS:

```text
DATABASE_URL=postgresql+psycopg://postgres.PROJECT:PASSWORD@POOLER:5432/postgres?sslmode=require
CHECKPOINT_URL=postgresql://postgres.PROJECT:PASSWORD@POOLER:5432/postgres?sslmode=require
```

Avoid the transaction pooler for this checkpointer configuration. Keep the API's pool small; the
worker/checkpointer uses an additional connection.

Run `scripts/supabase_lockdown.sql` in the dedicated project's SQL editor. It creates the private
`resumes` bucket, removes browser role access to public-schema tables, and sets conservative
default grants. Run it again after the first migration to enable RLS on all newly created tables.
The browser uses Supabase only through the backend authentication path; no direct business-table
policies are needed. Use a dedicated project because the lockdown affects all public-schema tables.

## 2. Create the Render services

Push this repository to a Git provider you control and connect it to a new Render Blueprint using
`render.yaml`. Set the backend variables requested by the Blueprint:

- `DATABASE_URL`, `CHECKPOINT_URL`, `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`.
- `FRONTEND_URL` to the exact frontend HTTPS origin, without a trailing slash.
- `API_URL` to the backend HTTPS origin.

The Blueprint starts with `AI_MODE=demo`, `EXTERNAL_MODE=preview`, and production Supabase
authentication. `APP_SECRET` is generated by Render; keep it stable across deployments.
Do not set `APP_ENV=local` to bypass missing configuration.

For the static site, set `VITE_API_URL` to the backend HTTPS origin, without `/api` or a trailing
slash, and rebuild. Its SPA rewrite sends candidate invitation URLs to `index.html`.

The backend applies Alembic migrations then seeds fictional data on an empty database. Initial
seeding uploads the twenty fictional resumes to private Storage. A missing bucket or invalid
storage key will fail startup instead of silently saving files on an ephemeral disk.

The health endpoint is `/api/health`; API docs are `/docs`. The public `/api/demo` response is a
fixed projection of the committed fictional fixtures, not mutable staff data.

## 3. Grant staff access

Using a trusted local environment with production configuration in an ignored `.env`, first apply
the migrations if the backend has not already deployed:

```powershell
.venv/Scripts/python.exe -m alembic -c backend/alembic.ini upgrade head
.venv/Scripts/python.exe scripts/provision_staff.py --id SUPABASE-USER-UUID --email you@example.com --name "Your Name" --role admin
```

The provisioning script only maps an existing Auth UUID to an application role. It does not create
or change passwords. Repeat for confirmed recruiter/manager accounts. Admins can change existing
staff roles in Settings; the last admin cannot be demoted. Assign manager accounts to relevant jobs
in the job editor.

Local sample identities are not provisioned in Supabase mode. Do not publish any staff password in
the README or the portfolio demonstration.

## 4. Turn on live test integrations

Follow the provider setup in the README. Set Gemini variables and choose `AI_MODE=gemini` only
after a one-resume free-quota test. Add Resend/Google credentials, owned-recipient allowlists,
`TOKEN_ENCRYPTION_KEY`, and choose `EXTERNAL_MODE=live` only when ready for real test actions.

For hosted Calendar, register the exact HTTPS backend callback URL. Add the same URL to
`GOOGLE_REDIRECT_URI`, connect from the hosted Settings page, and use an owned Google test user.
OAuth tokens are encrypted in PostgreSQL. Changing the encryption key requires reconnecting.

## 5. Release checks

1. Public view loads with twenty fictional candidates and no credentials/invitation tokens.
2. Unauthenticated mutation attempts fail; a manager cannot access an unassigned job.
3. Staff login works, a synthetic resume parses, and a screening pauses for review.
4. Redeploy the backend; the review still resumes and no completed extraction is repeated.
5. An invitation submits once, expires correctly, and exposes neither answer keys nor staff notes.
6. A test email reaches the configured signup inbox and a test interview reaches only owned calendars.
7. An occupied slot is rejected, a duplicate booking creates one event, and invalid OAuth requests fail.
8. Supabase bucket remains private and anon/authenticated PostgREST calls cannot read business tables.
9. Confirm billing remains disabled and free quotas are sufficient for the demonstration.

## Operating limits and recovery

Render Free sleeps after idle periods and may restart. Files and jobs live in Supabase, while temporary
processing files do not survive. Work resumes when a request wakes the API; no timed-reminder promise
is made. Supabase Free projects can pause after inactivity; restore them from the dashboard before a
presentation. Back up fictional seed inputs and migrations in Git, never secrets or live credentials.

The UI exposes failed processing and safe retry paths. An uncertain email must be inspected in Resend
before another action is created. Calendar uses a stable event ID to reconcile retries. Free quotas are
variable by account; stop on exhaustion rather than enabling billing to keep a demo running.

Actual provider credentials, account availability, hosted migrations, private-bucket policies, and email/
calendar delivery must be verified in your accounts. Local mocked tests cannot prove those settings.
